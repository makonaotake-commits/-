## ベンガルからの質問への回答：「記録の種類（体調／補液／投薬）」を分析イベントとして送ってよいか

**結論：条件付きで送ってよい（重大度：中）。** ただし、送らずに済むなら、そのほうが安全です。

**理由**
- このアプリは猫の CKD 専用なので、利用していること自体が、すでに「CKD の猫がいる」ことを示します。「補液」「投薬」という種類が加わると、治療の内容まで一段具体的になります。
- 一方で、送るのは猫のデータで、ランダムな ID としか結び付かず、値・薬の名前・メモは含みません。人の病歴などの要配慮個人情報にはあたらないと考えます（ロシアンの見立て。要件 NFR-PRV-02 と同じ）。
- そのため、次の条件を満たせば、K-4（補液・投薬のリマインダー完了率）の内訳を測る目的に見合うリスクだと判断します。

**送る場合の条件**
1. 種類は **固定の3つ（体調・補液・投薬）だけ** にする。補液の量・部位、薬の種類（錠剤など）、体調の項目名（嘔吐など）は送らない。
2. **1日単位で端末内で集計し、「日付・種類・件数」として送る** ことを推奨する（記録した時刻の細かい並びを送らない）。
3. ユーザーを識別するのはアプリが作るランダムな ID だけ。広告 ID・端末 ID は使わない（§5-2 の共通ルールどおり）。
4. 分析 SDK は、広告やほかのアプリのデータと結び付ける機能を持たない、またはその機能を無効にできるものを選ぶ。SDK 一覧（NFR-PRV-05）に、送信先の国と、提供者がデータをどう使うかを書く。
5. 設定画面とプライバシーポリシーの説明文に、種類を送ることを明記する。案：「アプリの使われ方（記録の種類〔体調・補液・投薬〕と件数など）を、改善のために送ります。記録の中身（値・お薬の名前・メモ）は送りません。」
6. **お休み中・一覧から外した猫の記録は、分析の対象にしない**（下の K-1）。

**送らない場合**：「記録を保存した」だけを送り、K-4 の内訳は聞き取りで補う（§5-3 の方法）。ロシアンとしてはどちらでも可で、決めるのはユーザーです（Q-27 と一緒に）。

## 追記：要件 NFR-PRV-11（コミット 7474b1e）との関係
本レビューと同時に、ブリショーが NFR-PRV-11 を追加しました。「判定は端末の中だけで行い、理由は送らない」という方向は適切です。ただし、「分析を入れる場合は『集計に含めるかどうか』の1つのフラグだけを送る」としている部分は、上の **K-1** と食い違います。フラグにまとめても、値が立つことで「何らかの理由でケアが止まった」ことが外に出るためです。
**修正案**：NFR-PRV-11 の後半を「該当する猫については、端末内でイベントそのものを送らない（フラグも送らない）」に改める。分析を入れる場合の第1弾の追加条件として扱い、要件のレビュー状態は `compliance_reviewed` のままとします（Q-27 で分析を入れることになった時点で、反映を確認します）。
