# 05 非機能要件

- 作成：ブリショー ／ 版：第2版（2026-11-09。ロシアンのレビュー `docs/compliance/review_2026-11-09_requirements.md` を反映） ／ レビュー状態：`draft`
- 数値目標はすべて **仮** です。技術選定・開発体制が決まった時点で見直します。

---

## 1. 対応環境

| ID | 要件 |
|---|---|
| NFR-ENV-01 | iPhone と Android の両方に対応する（`kickoff_answers.md` #7） |
| NFR-ENV-02 | 対応 OS は、各 OS の直近2〜3世代（仮）。シニアの飼い主さんの古い端末も考慮して、最終的に決める（→ `07` の Q-13） |
| NFR-ENV-03 | 3か月で両 OS に出すため、クロスプラットフォームの開発手法を第一候補にする（仮。技術選定は開発体制とあわせて決める） |
| NFR-ENV-04 | スマホの縦向きを基本にする。タブレットは表示崩れがないことだけを保証する（仮） |

## 2. 個人情報・セキュリティ（NFR-PRV / NFR-SEC）

| ID | 要件 |
|---|---|
| NFR-PRV-01 | 飼い主さんの情報（連絡先・端末識別子・利用する動物病院名など）は個人情報として扱う。猫の体調・検査値データも、飼い主さんと結びつくため、同じ水準で保護する |
| NFR-PRV-02 | 猫の健康データは個人情報保護法上の「要配慮個人情報」（人の病歴等）には当たらないと考えられる（**推測**。ロシアンの見立ても同じ）。ただし、ユーザーの信頼に関わるため、取り扱いは要配慮個人情報に準じて慎重に設計する。プライバシーポリシーの作成時に弁護士に確認する |
| NFR-PRV-03 | **猫の体調・ケア・検査値のデータを、広告のターゲティングや広告主への提供に使わない**（**仮の前提**。ユーザーに確認中 → `07` の Q-03）。F-01・プライバシーポリシー・ストアのプライバシー申告で同じ表現にし、将来変える場合は改めて同意を取る（ロシアン #17）。使う場合は、利用目的の明示と個別の同意取得が必要になる（`kickoff_answers.md` の注意点 → `07` の Q-03） |
| NFR-PRV-04 | 利用状況の分析ログには、記録の中身（体調の値・メモ・薬の名前）を含めない。件数・画面遷移・操作だけを記録する。メモ欄には飼い主さん自身の病歴なども書かれうるため、特に送らない（ロシアン #18） |
| NFR-PRV-05 | 外部 SDK（分析・クラッシュ報告・広告）を一覧にし、それぞれ送信する情報をプライバシーポリシーに明記する。各ストアのプライバシー申告と食い違わないようにする |
| NFR-PRV-06 | アプリ内から、データの書き出しと全削除ができる（F-09） |
| NFR-SEC-01 | 端末内のデータは、OS の暗号化機能で保護された領域に保存する |
| NFR-SEC-02 | クラウドを使う場合は、通信を TLS で暗号化し、保存時も暗号化する。アクセス権は最小限にする |
| NFR-SEC-03 | アプリのロック（端末の生体認証／パスコード）を任意で設定できる（Could・仮） |

## 3. 獣医療・法令（NFR-REG）

| ID | 要件 |
|---|---|
| NFR-REG-01 | ⚠️ 入力値にもとづく判定・評価・提案・基準値との比較を、どの画面にも出さない（`01` の §4）。新しい機能や文言を追加するときは、この点をロシアンが確認する |
| NFR-REG-02 | 飼い主向けの文言（画面・通知・ストアの説明文・PDF）は、ロシアンのレビュー（`compliance_reviewed`）を通してから公開する |
| NFR-REG-03 | 監修獣医師（ユーザー本人）がアプリの運営者でもあることを、アプリ内「このアプリについて」とストアの説明文で開示する（→ `07` の Q-05）。開示には **収益源**（ペットフード・療法食メーカーの広告。第1弾で広告がない場合は「将来、広告を掲載する予定」）と、**監修の範囲**（一般情報の確認であり、個別の診療はしない）を含める（ロシアン #23） |
| NFR-REG-05 | お問い合わせ・SNS で、個別の猫の病状・治療についての相談には答えない。案内用の定型文を用意する（無診察での診療を避けるため。ロシアン C-2 / D-6） |
| NFR-REG-04 | 「かかりつけの獣医師の指示を優先してください」という趣旨の文を、初回設定・レポート・読みもの（第2弾以降）に表示する。初回設定と設定画面には、症状を挙げない緊急時の一文も置く（F-01。ロシアン #19） |
| NFR-REG-06 | リリース前に、獣医師法・動物用医療機器プログラムの該当性（農林水産省の考え方）を、弁護士または薬事の専門家に確認してもらう。F-22・F-23 のような機能を加える場合は、着手前にロシアンが再レビューする（ロシアン #24。照会するかはユーザーが判断 → `07` の Q-20） |

## 4. 広告（NFR-ADS）

| ID | 要件 |
|---|---|
| NFR-ADS-01 | 広告は **記録画面と分ける**。記録の入力（S-04〜S-07）・振り返り（S-08）・検査値とグラフ（第2弾）・レポート（S-09）・お別れ後の画面と思い出（S-11）・はじめに（S-01）・通知には広告を表示しない（ロシアン B-1、ベンガル） |
| NFR-ADS-02 | 広告には「広告」「PR」の表示と **広告主名** を付け、アプリ側の情報（読みもの等）と見分けがつくようにする。広告を置くタブは「協賛・広告」など広告と分かる名前にし、「おしらせ」は使わない。運営からのお知らせを同じタブに混ぜない（ロシアン #15。景品表示法のステルスマーケティング規制） |
| NFR-ADS-03 | ⚠️ 療法食の広告は、「獣医師の指導のもとで与えるもの」であることが伝わる表示にする。効能・効果の表現はロシアンが確認する（薬機法〔動物用〕・景品表示法・ペットフードの表示ルール） |
| NFR-ADS-04 | 記録の内容（例：嘔吐が多い）に連動した広告は出さない（NFR-PRV-03 と同じ方針・仮） |
| NFR-ADS-05 | 「お別れ（見送り）」に設定したら、**その時点で広告をすぐに止める**（ロシアン E-1）。ほかに記録中の猫がいる場合に、いつ・どう再開するかは未決（→ `07` の Q-15） |
| NFR-ADS-08 | 第三者の広告 SDK は使わない（仮。ベンガル案）。広告は自社で配信する枠（協賛表示つき）とし、端末識別子や行動データを広告事業者に送らない |
| NFR-ADS-09 | **広告掲載基準** を定める（ロシアン #16）。最低限：①効能・効果をほのめかす表現（「腎臓に良い」等）と体験談を載せない、②療法食は「獣医師の指導のもとで与えるもの」と明記する、③サプリメント・動物用医薬品は受けない（NFR-ADS-07）、④恐怖訴求・罪悪感をあおる表現を載せない、⑤広告から記録画面への導線を作らない。詳細はロシアンが案を作る |
| NFR-ADS-10 | **広告の審査の流れ**（ロシアン #16）：広告主の入稿 → ロシアンのレビュー → 監修獣医師の確認 → 掲載。承認後に変更があれば再審査する。審査の記録を残す。広告主との契約に「コンテンツ・監修内容に関与しない」を入れる |
| NFR-ADS-11 | 広告を出す弾では、NFR-ADS-02・09・10 を **リリース条件** に入れる（→ `06` の DoD）。第1弾で広告を出さない場合は、第2弾の設計に引き継ぐ |
| NFR-ADS-07 | MVP では、サプリメント・動物用医薬品の広告は受けない（ロシアン B-3。最終判断はユーザー） |
| NFR-ADS-06 | 全画面広告・動画の自動再生・通知による広告は使わない（ゆとりある UX のため・仮） |

## 5. 使いやすさ・アクセシビリティ（NFR-UX）

| ID | 要件 |
|---|---|
| NFR-UX-01 | 文字サイズを3段階で変えられる。OS の文字サイズ設定にも追従する |
| NFR-UX-02 | 文字と背景のコントラストは WCAG 2.2 の AA 相当を目安にする |
| NFR-UX-03 | タップする部分は、iOS の推奨 44pt／Android の推奨 48dp 以上の大きさにする。主要な記録ボタンはさらに大きくする |
| NFR-UX-04 | **片手操作**：記録の主要な操作を、画面の下半分で完結させる（猫を抱えながら・補液しながらでも使えるように） |
| NFR-UX-05 | 色だけで意味を伝えない。「赤＝悪い」などの評価的な配色を使わない |
| NFR-UX-06 | 体調記録は、ホームから **2タップ以内**、所要 **30秒以内**（仮）で保存できる |
| NFR-UX-07 | 取り消し：保存後すぐの「元に戻す」を用意する。削除は確認を出す |
| NFR-UX-08 | スクリーンリーダー（VoiceOver / TalkBack）で、主要な記録操作ができる |

## 6. デザインとトーン（NFR-TONE）

`kickoff_answers.md` の自由記入をもとにしています。

| ID | 要件 |
|---|---|
| NFR-TONE-01 | 親しみやすく信頼感のある **シンプルなラインアート**。装飾を盛りすぎない |
| NFR-TONE-02 | 余白を多くとり、1画面の情報を絞る。せかす演出（カウントダウン、点滅、赤いバッジの多用、連続記録日数の表示）はしない |
| NFR-TONE-03 | 文言は「〜しましょう」「〜してください」の連続を避け、やわらかく短くする。罪悪感をあおる言葉（「忘れています」「途切れました」）は使わない |
| NFR-TONE-04 | ペットロスへの配慮：見送り関連の画面は、色・イラスト・言葉を落ち着いたものにする（例：明るいキャラクターの演出を出さない） |
| NFR-TONE-07 | 見送り関連の言葉は「見送った」「思い出」のような中立的な言葉を基本にする。「虹の橋」「天国」「お空」などの宗教的・定型的な表現は使わない（ロシアン #13） |
| NFR-TONE-06 | 禁止語リスト（「治る」「回復」「悪化」「危険」「手遅れ」「飼い主のせい」と受け取れる表現など）をロシアンと作り、画面・通知・PDF の文言チェックに使う（ロシアン E-3） |
| NFR-TONE-05 | アニメーションは控えめにする。OS の「視差効果を減らす」設定に従う |

## 7. 性能・可用性・オフライン（NFR-PERF / NFR-OFF）

| ID | 要件 |
|---|---|
| NFR-PERF-01 | アプリの起動から、ホームの表示まで2秒以内（仮・中位機種） |
| NFR-PERF-02 | 1か月分のレポート PDF を、10秒以内（仮）に作れる。操作全体で1分以内 |
| NFR-OFF-01 | 記録・振り返り・リマインダー・PDF 作成は、**オフラインでも使える**（第1弾は端末内保存が前提・仮） |
| NFR-OFF-02 | リマインダーは端末内の通知で動かし、サーバーが止まっても届くようにする |
| NFR-AVL-01 | クラウド機能（バックアップ等）を使う場合も、それが止まっていることで記録ができなくなってはいけない |

## 8. データ・保守

| ID | 要件 |
|---|---|
| NFR-DATA-01 | 日時はタイムゾーンつきで保存する（旅行・引っ越しでもずれないように） |
| NFR-DATA-02 | 単位（kg・mL、第2弾の検査値の単位）を値とセットで保存する |
| NFR-DATA-03 | アプリを更新しても記録が失われないよう、データ移行のテストをリリースごとに行う |
| NFR-DATA-04 | 文言は1か所で管理し、ロシアンのレビュー結果を反映しやすくする |
